## Часть 1. Дополнение схемы данных

В модель данных добавлены две новые сущности, расширяющие функционал предметной области:

1. **`project_member` (Участники проекта / реализация связи M:N)**:
   * Реализует прямую связь «многие ко многим» между `project` и `employee`.
   * Содержит составной первичный ключ `PRIMARY KEY (project_id, employee_id)`, гарантирующий невозможность повторного добавления одного сотрудника в один и тот же проект.
   * Фиксирует атрибуты участия: дату назначения `joined_at` и роль сотрудника `role` с ограничением `CHECK (role IN ('Manager', 'Developer', 'QA', 'DevOps', 'Designer'))`.

2. **`task_history` (История изменения статусов задач)**:
   * Реализует журнал аудита под частый бизнес-запрос №4 из ДЗ №1 («Показать историю изменения статуса задачи: кто, когда и почему изменил»).
   * Атрибуты: `history_id` (PK), `task_id` (FK), `status_id` (FK), `changed_by_employee_id` (FK), `change_reason` (TEXT), `changed_at` (TIMESTAMP).

### Реализация отношения Many-to-Many (M:N) и эффект DROP CASCADE
* **Выбор способа реализации:** Отношение $M:N$ реализовано классической соединительной таблицей (*junction table*) `project_member`. Данный подход исключает дублирование записей, обеспечивает соответствие третьей нормальной форме (3НФ) и позволяет хранить индивидуальные метаданные связи (роль и время добавления).
* **Поведение при DROP CASCADE:**
  * Если выполнить DDL-команду `DROP TABLE project CASCADE;`, СУБД PostgreSQL удалит саму таблицу `project`, а также автоматически снимет внешний ключ (`FOREIGN KEY`), ссылавшийся на нее из `project_member`. Таблица участников останется существовать, но потеряет ссылку на родителя.
  * На уровне данных внутри строк используется правило `ON DELETE CASCADE`: при удалении строки проекта через `DELETE FROM project WHERE project_id = ...` все ассоциированные строки участников в `project_member` удаляются сервером автоматически, предотвращая появление записей-сирот.

## Часть 2 и 3. Документирование нарушений ограничений целостности

Ниже представлена сводная таблица перехвата пяти типов ограничений целостности из скрипта `02_constraints_demo.sql`:

| № | Ограничение | Выполняемый запрос (SQL) | Сообщение СУБД (SQLERRM) | Понятное сообщение для пользователя | Как исправить |
|---|---|---|---|---|---|
| 1 | **CHECK** | `INSERT INTO project (..., start_date, deadline) VALUES (..., '2026-11-01', '2026-10-01')` | `new row for relation "project" violates check constraint "project_check"` | Бизнес-ошибка: Дедлайн проекта не может быть раньше даты его начала. | Указать дату дедлайна, которая больше или равна дате старта. |
| 2 | **FOREIGN KEY** | `INSERT INTO task (project_id, ...) VALUES (999999, ...)` | `insert or update on table "task" violates foreign key constraint "task_project_id_fkey"` | Бизнес-ошибка: Нельзя создать задачу в несуществующем проекте. | Указать существующий идентификатор `project_id` из таблицы `project`. |
| 3 | **UNIQUE** | `INSERT INTO employee (..., email) VALUES (..., 'ivan.unique@example.com')` (повторно) | `duplicate key value violates unique constraint "employee_email_key"` | Бизнес-ошибка: Пользователь с таким адресом электронной почты уже зарегистрирован. | Указать уникальный адрес электронной почты сотрудника. |
| 4 | **NOT NULL** | `INSERT INTO employee (first_name, last_name, email) VALUES ('Алексей', NULL, ...)` | `null value in column "last_name" of relation "employee" violates not-null constraint` | Бизнес-ошибка: Фамилия сотрудника является обязательным полем и не может оставаться пустой. | Передать непустую текстовую строку в поле `last_name`. |
| 5 | **PRIMARY KEY** | `INSERT INTO project_member (project_id, employee_id) VALUES (v_id, v_emp)` (повторно) | `duplicate key value violates unique constraint "project_member_pkey"` | Бизнес-ошибка: Сотрудник уже назначен участником этого проекта (дублирование составного ключа). | Не добавлять строку повторно либо обновлять роль существующей записи через `UPDATE`. |
