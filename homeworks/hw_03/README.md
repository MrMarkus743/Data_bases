## Q1. Уникальные рейсы и сортировка

### 1. Сравнение DISTINCT и GROUP BY
* **Итоговый результат:** Запросы возвращают абсолютно одинаковый список номеров рейсов.
* **План выполнения (`EXPLAIN`):** В современных версиях PostgreSQL оптимизатор понимает, что `DISTINCT` применяется ко всей строке, и строит для обоих запросов один и тот же план — через узел `HashAggregate` (или `Sort` -> `GroupAggregate`).
* **Разница в применении:** `DISTINCT` просто убирает повторяющиеся строки. `GROUP BY` нужен тогда, когда к группам требуется применить расчетные агрегатные функции (`COUNT`, `SUM`, `AVG`).

### 2. Сортировка по умолчанию и регистр символов
* **Почему не нужен `ASC`:** По стандарту SQL и в PostgreSQL сортировка `ORDER BY` по умолчанию всегда работает по возрастанию (`ASC NULLS LAST`), поэтому дописывать `ASC` вручную необязательно.
* **Сортировка регистра ('PG0001' и 'pg0001'):** Поведение зависит от настроек локали (`LC_COLLATE`):
  * В стандартной локали `C` (по байтам ASCII) заглавные буквы идут раньше строчных, поэтому `'PG0001'` будет выше `'pg0001'`.
  * В языковых локалях (например, `ru_RU` или `en_US`) буквы сортируются по правилам алфавита: одинаковые буквы идут рядом, а регистр учитывается во вторую очередь.

## Q2. Аэропорты и выручка за билеты

### 1. Учет пассажиров с двумя билетами на один рейс
* **Расчет выручки (`SUM(amount)`):** Выручка считается корректно: если куплено два места, в таблице `ticket_flights` будут две записи с суммами, и обе войдут в общую сумму.
* **Подсчет пассажиров:** Если использовать `COUNT(*)` или `COUNT(ticket_no)`, запрос посчитает количество **проданных мест** (один человек посчитается дважды). Чтобы посчитать количество именно **физических пассажиров**, нужно использовать `COUNT(DISTINCT passenger_id)`.

### 2. Рейсы без проданных билетов
* **Какой JOIN использовать:** Обязательно `LEFT JOIN` (от таблицы рейсов `flights` к таблице билетов `ticket_flights`).
* **Почему не подходит `INNER JOIN`:** Внутреннее соединение оставляет только те строки, у которых есть пара в обеих таблицах. Если на рейс не продано ни одного билета, `INNER JOIN` просто удалит этот рейс из итогового отчета.
* **Вывод нулевой выручки:** Для пустых рейсов `SUM(amount)` вернет `NULL`. Чтобы в отчете отображался ноль, значение оборачивается в функцию `COALESCE(SUM(amount), 0)`.

## Q3. Отмененные рейсы и города

### 1. Города с аэропортами без рейсов
* **Логика предметной области:** Если аэропорт есть в справочнике `airports`, но из него вообще не было рейсов, значит, отмененных рейсов из него тоже не было (0 отмен). Следовательно, такой город **обязан попасть** в итоговый список.
* **Как реализовать:** Через проверку `NOT EXISTS`:
  ```sql
  SELECT DISTINCT a.city
  FROM bookings.airports a
  WHERE NOT EXISTS (
      SELECT 1 
      FROM bookings.flights f
      WHERE f.departure_airport = a.airport_code 
        AND f.status = 'Cancelled'
  );
  ```
  Для города без рейсов подзапрос вернет 0 строк, `NOT EXISTS` вернет `TRUE`, и город останется в ответе.

### 2. Опасность NOT IN при наличии NULL
* **В чем ловушка:** В SQL сравнение с `NULL` возвращает неопределенность (`UNKNOWN`). Конструкция `val NOT IN (1, 2, NULL)` вычисляется как:  
  `val != 1 AND val != 2 AND val != NULL`.  
  Так как последняя часть дает `UNKNOWN`, всё выражение целиком становится `UNKNOWN`.
* **Результат:** Блок `WHERE` пропускает только значения `TRUE`. Если подзапрос внутри `NOT IN` выдаст хотя бы один `NULL`, весь запрос вернет **пустой результат** (0 строк).
* **Почему `NOT EXISTS` надежнее:** Он проверяет только факт наличия строк (есть запись или нет) и не ломается от значений `NULL` внутри колонок.

## Q4. Места на борту и дубликаты

### 1. Дублирование пассажиров при двух посадочных
* **Как убрать дубли:** Использовать `DISTINCT` по идентификатору пассажира (`passenger_id`) либо сгруппировать через `GROUP BY`.
* **Что эффективнее:** Если нужно только вывести уникальный список людей — проще и быстрее написать `SELECT DISTINCT`. Если в будущем потребуется добавить подсчеты (например, сколько мест занял) — удобнее использовать `GROUP BY`. На уровне плана СУБД выполнит их одинаково (через хэширование).

### 2. Аномалия: сдан билет, но остался посадочный талон
* **Поведение при обычном цепочечном соединении:**  
  Связь идет по цепочке `tickets` -> `ticket_flights` -> `boarding_passes`. Если запись о билете удалена из промежуточной таблицы `ticket_flights`, то `INNER JOIN` потеряет всю строку, и пассажир не попадет в отчет.
* **Поведение при прямом соединении:**  
  Если связать `tickets` напрямую с `boarding_passes` по номеру билета (`ticket_no`), пассажир отобразится в списке, что позволит обнаружить расхождение между билетами и посадкой.

## Q5. DDL и блокировки на живой таблице

### 1. Блокировки при выполнении ALTER TABLE
* **Что произойдет:** Команда `ALTER TABLE` встанет в очередь ожидания и «повиснет».
* **Причина:** Длинный `SELECT` держит слабую блокировку на чтение (`AccessShareLock`). Команда изменения таблицы `ALTER TABLE` требует самую строгую блокировку — `AccessExclusiveLock`. Она не может начаться, пока активен `SELECT`.
* **Опасность:** Пока `ALTER TABLE` ждет завершения аналитики, все новые входящие запросы к таблице встают в очередь за ней, из-за чего база может быстро исчерпать доступные подключения.

### 2. Добавление колонки с DEFAULT в PostgreSQL 11+
* **Почему выполняется мгновенно:** Начиная с версии PostgreSQL 11 добавление столбца со значением по умолчанию не переписывает физически всю таблицу на диске.
* **Как это устроено:** Новое значение `DEFAULT` просто записывается в системный каталог (`pg_attribute`). При чтении старых строк с диска база данных подставляет это значение на лету.
* **Что будет при изменении DEFAULT на true:** Все ранее созданные строки так и останутся со значением `false`. Значение `true` будет проставляться только для новых записей при операции `INSERT`.

### 3. Индексация без блокировки (CONCURRENTLY)
* **Почему стандартный CREATE INDEX блокирует запись:** Он накладывает блокировку `ShareLock`, которая позволяет читать таблицу, но запрещает любые изменения (`INSERT`, `UPDATE`, `DELETE`) до завершения построения.
* **Как делать без простоя:** Использовать команду конкурентного построения:
  ```sql
  CREATE INDEX CONCURRENTLY idx_flights_status ON bookings.flights(status);
  ```
* **В чем компромисс:**
  1. Индекс строится в два прохода, поэтому общее время создания заметно дольше.
  2. Команду `CONCURRENTLY` нельзя запускать внутри явного блока транзакции (`BEGIN ... COMMIT`).
  3. Если в процессе возникнет сбой, в базе останется нерабочий индекс со статусом `INVALID`, который придется удалять вручную.

## Q6. Агрегация и NULL в вычислениях

### 1. Влияние NULL на расчет среднего времени задержки (AVG)
* **Поведение функции:** Для отмененных и невылетевших рейсов время `actual_departure` равно `NULL`, поэтому разность со временем по расписанию также дает `NULL`.
* **Исключение из расчета:** Агрегатная функция `AVG` автоматически игнорирует строки со значением `NULL`.
* **Влияние на показатель:** База делит сумму задержек не на все рейсы в таблице, а только на те, которые **фактически состоялись**. Это дает честное среднее время опоздания реально вылетевших самолетов.

### 2. Сравнение COUNT(aircraft_code) и COUNT(*)
* **Разница в логике:**
  * `COUNT(*)` считает общее количество строк в выборке.
  * `COUNT(aircraft_code)` считает количество строк, где значение в колонке `aircraft_code` не равно `NULL`.
* **Будут ли результаты одинаковыми:** В учебной базе на столбце `aircraft_code` стоит ограничение `NOT NULL` (у каждого рейса обязательно указан самолет). Поэтому оба запроса вернут абсолютно одинаковое число. Разница возникнет только в том случае, если с колонки снять ограничение и в данных появятся пустые значения.
